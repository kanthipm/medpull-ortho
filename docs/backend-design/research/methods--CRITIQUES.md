# methods — adversarial critiques


## Verdict
The methods research is strong; the deployment reasoning is largely fictional, and fictional in ways this specific codebase punishes immediately. Three facts from the repo invalidate assumptions shared across all seven reports. (1) GET /worklist (backend/app/api/worklist.py:34-56) loops over EVERY patient calling ensure_fresh_assessment, and compute_input_hash (backend/app/engine/pipeline.py:44) folds date.today() into the hash — so the first console load each morning recomputes the whole panel inside ONE request with a 30s Lambda timeout (infra/cloudformation.yaml:217) behind a 30s CloudFront origin read timeout. Every per-patient method proposed (Kalman MLE, BOCPD, GP with n_restarts_optimizer=3, MEWMA, conformal) is individually cheap and collectively fatal at N patients in one request. (2) scipy is DELIBERATELY EXCLUDED from the Lambda artifact and infra/build-lambda.sh contains a grep guard that hard-fails the build if app/ imports it — so 'statsmodels is pure numpy/scipy, Lambda-safe', 'scipy>=1.11 (already a dependency)' and 'scikit-learn adds ~30 MB' are all wrong as stated; the build script's own exit 1 at 250 MB unzipped is the referee. (3) There is NO scheduler anywhere in infra/cloudformation.yaml — no EventBridge rule, no cron. Scoring is lazy-on-read or on webhook ingest inside the 30s API function. Every lead-time claim in the research ('3-day median lead', '4.4 +/- 3.1 days') presupposes an alert that fires when data arrives; today an alert exists only if a clinician opens the page. The correct next six weeks: build the nightly scoring Lambda and the outcome/adjudication schema FIRST (both zero-model work with multi-year lead times), move every heavyweight fit into that batch path and serve frozen coefficients as numpy dot products in the request path, and ship exactly three engine changes — moderated-variance baselines, a single episode arbiter with an alert budget enforced by a CI replay test, and the LLM numeric-consistency validator. Everything else on the list is a roadmap item that should not touch app/engine/ this quarter.

### Objections

**TARGET:** All seven reports — implicit assumption that per-patient compute is free in the request path (Kalman/statsmodels MLE, BOCPD, GaussianProcessRegressor with n_restarts_optimizer=3, MEWMA, conformal, cosinor)

- **OBJECTION:** None of the reports read the read path. GET /worklist iterates every Patient and calls ensure_fresh_assessment (backend/app/api/worklist.py:34-56); compute_input_hash includes date.today() (backend/app/engine/pipeline.py:44), so every patient is stale at midnight. The first clinician to open the console each morning triggers a full-panel recompute inside one HTTP request. ApiFunction Timeout is 30s (infra/cloudformation.yaml:217) and CloudFront OriginReadTimeout is 30s, so there is no slack — it 504s at the edge. A GP with 3 optimizer restarts across 6 metrics is roughly 0.5-3s per patient on its own; UnobservedComponents.fit(method='lbfgs', maxiter=200) is another 0.2-1s per metric.
- **CONSEQUENCE:** At 60-100 patients the morning worklist times out every single day. Clinicians see a broken roster at exactly the moment of highest use, conclude the product is unreliable, and stop opening it. This is the failure mode that kills the product before any alert-quality question is ever reached.
- **FIX:** Split the paths before adding any method. Add an EventBridge Scheduler rule invoking a scoring Lambda modelled on the existing SeedFunction (Timeout 900, same artifact, infra/cloudformation.yaml:249-266) that writes RiskAssessment rows nightly. Make /worklist a pure read — delete the ensure_fresh_assessment call from the loop and drop date.today() from the input hash. Then enforce a hard per-patient request-path budget of 50ms with a pytest benchmark that fails CI, and put anything exceeding it in the nightly job.

**TARGET:** 'statsmodels>=0.14 — pure numpy/scipy, installs in a Lambda zip, ~15 MB'; 'scikit-learn adds ~30 MB to the Lambda bundle — acceptable'; 'scipy>=1.11 (already a dependency; present in backend/.venv)'

- **OBJECTION:** scipy is explicitly excluded from the deployment artifact. infra/build-lambda.sh line 37 EXCLUDE regex ends in '|scipy)==' with the comment 'declared in pyproject but imported nowhere in app/ ... the single largest wheel in the tree', and lines 43-46 run a grep guard that exits 1 if app/ imports scipy. statsmodels requires scipy and patsy; scikit-learn requires scipy, joblib and threadpoolctl. The real aarch64 unzipped cost is scipy ~90-110 MB plus sklearn ~40 MB plus statsmodels ~25 MB on top of numpy+pandas which already dominate the current bundle. build-lambda.sh checks unzipped size and exits 1 above 250 MB.
- **CONSEQUENCE:** The first PR that adds `import statsmodels` to app/engine/ fails the deploy build with a cryptic grep-guard error, and the fix (unexclude scipy) either blows the hard 250 MB unzipped limit or adds 3-6 seconds of cold-start import time against a 30s timeout. Someone will spend two days on this and then revert.
- **FIX:** Declare a rule and encode it: the request-path artifact is numpy + pandas only, forever. Fit everything else offline (a separate container-image Lambda or local batch), persist the outputs as JSON — spline coefficients, pooled LedoitWolf covariance, Platt (a,b), conformal calibration quantiles, MixedLM variance components — versioned in S3, and evaluate them in Lambda as numpy dot products. Extend the existing build-lambda.sh grep guard to also reject sklearn/statsmodels/pymc/numpyro/torch/lightgbm/ruptures/stumpy in app/, so the rule is enforced by the build rather than by memory.

**TARGET:** NightSignal '3-day median lead time'; Tilquin '4.4 +/- 3.1 days of lead time'; the entire alerting premise

- **OBJECTION:** There is no scheduler. grep for Schedule/Rule/cron/rate( over infra/cloudformation.yaml returns only an unrelated CloudFront cache Rules block. Recompute happens in two places: lazily when someone reads (worklist.py:17-24) and in a loop inside the webhook handler (backend/app/api/webhooks.py:192-195) which runs in the 30s API function. Nothing pushes. Lead time is defined as detection-before-clinical-presentation; if nothing computes or notifies until a human opens a page, measured lead time is bounded by clinician browsing habits, not by the detector.
- **CONSEQUENCE:** You ship a detector with a published 3-day lead, measure zero lead in the field, and cannot tell whether the algorithm or the plumbing failed. Worse, a patient deteriorating over a weekend generates no alert at all until Monday, which is a patient-safety claim you cannot defend in a partner conversation.
- **FIX:** Nightly EventBridge -> scoring Lambda, plus an actual outbound channel wired to tier transitions (the notifications model already exists at backend/app/api/notifications.py). Instrument time-from-observation-timestamp to time-of-clinician-acknowledgement as a first-class metric and report THAT, not the paper's lead time. Do not quote any lead-time figure in a clinical conversation until this metric exists.

**TARGET:** 'Backfills = Step Functions Map over patient-date ranges, backfill concurrency 10'; SAFFRON/ADDIS online FDR; ACI alpha_t state; the episode state machine with snooze and hysteresis

- **OBJECTION:** The database is a single SQLite FILE synced whole between /tmp and S3 under a global lock (DATABASE_URL sqlite:////tmp/recovery.db, S3_DB_KEY db/recovery.db, S3_LOCK_KEY db/recovery.db.lock, LOCK_TTL_SECONDS 900 for the seeder; backend/app/main.py:68-72 S3SqliteMiddleware). Ten concurrent writers each download, mutate and re-upload the entire database. Last writer wins and the other nine backfills vanish silently. Separately, SAFFRON's alpha-wealth depends on the actual ordered sequence of tests performed — under lazy-on-read scoring that sequence depends on which charts a clinician happened to open, which is not reproducible and breaks the FDR guarantee outright.
- **CONSEQUENCE:** Backfills silently lose 90% of their writes with no error, and you discover it months later when a validation replay does not reproduce production scores. The online-FDR guarantee is void but still reported to clinicians as '10% of today's list is expected false', which is a claim you would have to retract.
- **FIX:** Set batch concurrency to 1 until the store is Postgres — write it into the Step Functions definition, not a comment. Add a hard architectural rule: every detector must be a pure function of (observation history, as-of date), so replay equals production. That rule permits NightSignal, EWMA, CUSUM, BOCPD and ACI (all replayable) and forbids SAFFRON/ADDIS and any wealth-accumulating scheme until scoring is a deterministic nightly job on a real database. Daily Benjamini-Hochberg over the nightly batch is replayable and is sufficient at this panel size.

**TARGET:** 'Audit events export daily as JSONL to S3 with bucket versioning + Object Lock (COMPLIANCE mode), retention 7 years'

- **OBJECTION:** On this architecture the DataBucket holds the whole-file patient database, and S3SqliteMiddleware rewrites that object on writes. Applying Object Lock COMPLIANCE to that bucket creates a new immutable version of the ENTIRE PHI database on every sync, retained 7 years, deletable by nobody — not even the account root. COMPLIANCE mode is specifically the mode that cannot be shortened or overridden.
- **CONSEQUENCE:** You build an unbounded, un-deletable archive of full patient databases. The first patient data-deletion request, the first BAA negotiation, or the first accidental ingest of wrong-patient data becomes unfixable. This converts a governance recommendation into a permanent liability.
- **FIX:** Object Lock belongs on a separate prefix or bucket containing ONLY small append-only audit events — one JSON object per scoring run with input snapshot hash, feature vector, engine git SHA, config version, tier and reason codes. Never on the DB prefix. Use GOVERNANCE mode, not COMPLIANCE, until counsel signs off, and write and test a documented deletion runbook before enabling either.

**TARGET:** The whole text-extraction stack (schema-constrained LLM over verbatim patient utterances with mandatory evidence spans), routed via 'Groq as fallback'

- **OBJECTION:** The deployed default chain is Groq (infra/cloudformation.yaml sets GROQ_API_KEY_PARAMETER and GROQ_MODEL llama-3.3-70b-versatile as live config; OLLAMA_URL is deliberately empty on Lambda). Groq does not offer a BAA at the standard commercial tier. The proposed extractor deliberately sends VERBATIM patient utterances plus mandatory verbatim evidence spans — the maximally identifiable form of the text — to that endpoint. One report notes the BAA condition in prose and then places Groq in the stack anyway, which is how this ships.
- **CONSEQUENCE:** PHI leaves the covered boundary to a vendor with no BAA. That is not a performance bug you iterate on; it is a reportable breach and it ends the partner-practice conversation that the entire prospective-cohort plan depends on.
- **FIX:** Enforce it in code, not prose. Add an env flag that defaults to DENY for any request whose payload contains free-text patient content, and route such calls only to a BAA-covered endpoint (Bedrock in-region, or Amazon Comprehend Medical which is HIPAA-eligible). Add a unit test that asserts the Groq client is unreachable from the check-in extraction path. Until that exists, ship only the deterministic medspaCy/regex red-flag layer, which needs no LLM and no BAA and is the safety-critical layer anyway.

**TARGET:** 'Deterministic guard: on device_model or firmware_version change, suppress flags for 3 days, re-estimate the baseline offset, reset CUSUM'

- **OBJECTION:** Two problems. First, Observation has no device_model or firmware_version column today — the guard is unimplementable without a schema migration nobody scheduled. Second, and more importantly, an offset correction is the wrong repair for a vendor switch. Apple wrist temperature deviation, Fitbit relative skin temperature, and any third vendor differ in reference, sampling window and definition; 'resting HR' and RMSSD are computed over different windows by different firmware. Re-centering the mean fixes the offset but leaves the SD and the metric SEMANTICS wrong, and baseline.py then applies an SD floor (SD_FLOORS_ABS / SD_FLOORS_REL, backend/app/engine/baseline.py:13-26) tuned for the old device, so a noisier new device reads as pathological indefinitely. Contralateral surgery is not addressed at all: it simultaneously invalidates the pre-op baseline AND the expected recovery curve AND resets postop_day, and nothing in the stack detects it.
- **CONSEQUENCE:** A patient who upgrades their watch at week 4 becomes a permanent false-positive generator; the clinician learns that alerts on that patient mean nothing and generalizes that lesson to the product. A patient having the other knee done shows a catastrophic trajectory deviation that is entirely expected, and either fires a high alert or teaches the clinician to ignore trajectory codes.
- **FIX:** Ship the schema now: device_model, firmware_version, metric_source and a vendor namespace on every Observation, plus a surgical_event table so a second procedure resets postop_day. Then treat a vendor change as baseline INVALIDATION, not 3-day suppression — restart the baseline in borrowed-prior mode (population prior, wide interval), mark the patient low-confidence for 14 days, and emit a DEVICE_CHANGED reason code that is visible in the UI. Never compare HRV, skin temp or SpO2 across vendors at all; require re-baselining. Firmware-only changes get the 3-day suppression; vendor changes do not.

**TARGET:** confidence.py / risk.py handling of the patient who stops wearing the device because they feel ill

- **OBJECTION:** The reports contradict each other — one says 'suppress the SCORE, never the ALERT', another says non-wear must be a covariate that RAISES risk — and the code does neither. coverage() returns LOW below 0.4 (backend/app/engine/confidence.py:14-17) and score_risk returns RiskLevel.MISSING_DATA (backend/app/engine/risk.py:61), which TIER_ORDER in worklist.py:14 ranks at position 2, BELOW both HIGH and MEDIUM. So a previously-adherent patient who abruptly goes dark ranks under a mildly elevated patient. Informative censoring is the single best-documented failure mode in remote monitoring and the current sort order actively buries it.
- **CONSEQUENCE:** The patient most likely to be deteriorating — the one who felt bad enough to stop wearing the watch — sinks to the bottom of the morning list. When that patient is later readmitted, the audit trail shows the system had the signal and de-prioritized it. That is the case that ends a pilot.
- **FIX:** Make disengagement its own detector, not an absence of one. Add a COVERAGE_COLLAPSE reason code that fires when 7-day coverage drops by >=40 percentage points versus the prior 7 days in a patient whose prior coverage was >=0.6, and rank it at MEDIUM or higher. Change TIER_ORDER so MISSING_DATA never sorts below LOW. Enforce a UI invariant: low confidence renders as 'we cannot see this patient', never as a reassuring statement. All three are hours of work.

**TARGET:** 'NightSignal: night_window = (00:00, 07:00); require step_count == 0; require >= 4 valid night-hours'

- **OBJECTION:** Whose clock, and does the data even exist? On timezone: wearable aggregators return device-local time for some endpoints and UTC for others; a patient flying EST to PST shifts their sleep midpoint three hours and a fixed wall-clock window then samples a different circadian phase, producing a clean spurious RHR step exactly like the +3 bpm yellow trigger. DST does the same to everyone at once. Compounding it, pipeline.py:44 uses date.today() — server-local, i.e. UTC on Lambda — while postop_day is derived from patient dates, so a Hawaii patient's day rolls over at 14:00 local. On data availability: NightSignal needs overnight HR restricted to zero-step MINUTES, i.e. intraday resolution, but the engine loads daily aggregates (backend/app/engine/dataload.load_daily_series). If your connectors return a daily resting-HR scalar, NightSignal as published cannot be implemented at all.
- **CONSEQUENCE:** Either you cannot build it (daily data only), or you build something materially different from the published algorithm while quoting its 80%/87.7% numbers, or you build it correctly and every business traveller and every DST transition generates a red alert. All three outcomes are bad; the third is the one that trains clinicians to dismiss the headline detector.
- **FIX:** Verify intraday HR plus per-minute steps per connector BEFORE scoping this. If unavailable, implement the two-threshold streaming-median state machine on daily resting HR, call it that, and stop citing NightSignal's performance. If available: store an IANA timezone per patient, define the night window relative to the patient's own detected sleep midpoint rather than wall clock, replace date.today() with a patient-timezone-aware date, and add a TZ_SHIFT reason code that suppresses HR and temperature flags for 3 days after a >=2h sleep-midpoint shift.

**TARGET:** The union of every proposed detector, versus the stated budget of '<=0.5 false episode-openings per patient-month'

- **OBJECTION:** Nobody added them up. Running simultaneously: NightSignal yellow at +3 bpm on a SINGLE night; EWMA 2-consecutive; CUSUM; BOCPD firing whenever P(r<3)>0.5; MEWMA; conformal at p<=0.05 which BY CONSTRUCTION averages 1 flag per 20 patient-days (~1.5/patient-month) on uneventful patients — that alone is 3x the stated budget before any other detector fires; trajectory deviation; and a red-flag text matcher explicitly tuned to recall >=0.95 with 'an explicit accepted false-positive rate'. The Ghomrawi and Hua numbers quoted in the research (387-438 false positives across a few hundred patient-weeks) are the honest prior here.
- **CONSEQUENCE:** At 100 patients this is plausibly 100-300 notifications per week. Published CDS override rates of 49-96% are the documented endpoint. Once clinicians learn to dismiss the list, the product is inert and no amount of later algorithm improvement recovers it, because nobody is reading.
- **FIX:** One arbiter, enforced in CI. Detectors emit typed EVIDENCE into a single episode state machine; only an episode opens an alert; cap at one open episode per patient with hysteresis and a snooze that escalation voids. Write a pytest that replays a synthetic 100-patient x 90-day uneventful cohort (and, week one, the free LifeSnaps and PMData cohorts, where every alert is by construction false) through the full stack and FAILS THE BUILD if alerts per patient-month exceeds the budget. The budget then constrains parameters instead of being contradicted by them.

**TARGET:** 'Mondrian split conformal ... needs ZERO adverse-outcome labels — that is the point'; 'calibration set = all patient-days from patients who completed recovery with no adverse event'

- **OBJECTION:** This is a logical error. Knowing a patient completed recovery with no adverse event is a negative label, and obtaining it requires the same 90-day follow-up, chart review and adjudication as a positive label. Today the schema records no outcome of any kind, so the set of 'uneventful completed recoveries' is not merely small — it is unknowable. The same error appears in the drift/monitoring plan's 'frozen reference of healthy patient-days'.
- **CONSEQUENCE:** The team schedules conformal calibration for month 2 on the belief it is label-free, discovers at month 2 that it cannot construct a calibration pool, and the honest false-alarm-rate claim — the single best idea in the research — slips a year.
- **FIX:** Say plainly that conformal needs NEGATIVE labels and start capturing them now. Ship an outcomes table this sprint: adjudicated_event (type, date, adjudicator, kappa), last_known_contact date, follow_up_complete boolean, plus engine git SHA and config version stamped on every score. That is days of work with a multi-year lead time and it is the highest-priority item on the entire list. In the interim, calibrate against the free external cohorts (LifeSnaps n=71, PMData n=16) where absence of surgery makes every day uneventful by construction, and label the resulting p-values as externally calibrated.

**TARGET:** Serving story for the eventual supervised model — BalancedRandomForest(n_estimators=500), LightGBM, TabPFN, PyMC/NumPyro posteriors

- **OBJECTION:** Only the discrete-time hazard report got this right ('serve inference in the Lambda as a pure numpy dot product of frozen coefficients — do NOT ship statsmodels or sklearn into the deployment artifact'). The others implicitly assume the fitted object is loadable at inference. A 500-tree BRF pickle requires sklearn plus scipy in the artifact; TabPFN requires torch; PyMC posteriors require either PyTensor with a runtime C++ compiler (impossible on a zip Lambda) or a precomputed summary. Separately, every one of these is gated on 30-100+ adjudicated events, which at single-digit-percent prevalence is 1,000-2,000 monitored patients — two-plus years at your stated 10-1000 scale.
- **CONSEQUENCE:** Engineering time gets spent evaluating models that cannot be served and cannot be trained, while the plumbing that would make them possible in 2028 (nightly scoring, outcome capture, device metadata, patient timezone) stays unbuilt.
- **FIX:** Adopt the discrete-time hazard report's serving contract universally and write it into CLAUDE.md: models are FIT offline, EXPORTED as coefficient JSON, and EVALUATED in Lambda with numpy. Under that contract, penalized logistic, Firth logistic, pooled-logistic hazard, spline curves and Platt scaling all ship; BRF, LightGBM, TabPFN and raw PyMC posteriors do not, so drop them from the plan rather than sequencing them. Revisit only when adjudicated event count crosses 100, and put that number on a dashboard so the gate is observable rather than remembered.

### Endorsed
- Keeping EWMA (lambda=0.3, L=2.66) with the mandatory 2-consecutive-day rule and one-sided CUSUM (k=0.5, h=5.0), and re-framing their limits as a false-alarm budget verified by Monte Carlo ARL simulation in CI. The 2-consecutive rule really is load-bearing and the existing implementation (backend/app/engine/deviation.py) is sound.
- Replacing the hard SD floors in backend/app/engine/baseline.py with moderated empirical-Bayes variance (nu0=8 pseudo-observations, robust scale via MAD or Huber c=1.345, median centre, device-resolution hard floor only). Closed form, numpy only, request-path safe, ships in a week, and it strictly dominates the current hand-set constants.
- Parametric empirical Bayes shrinkage for the baseline mean with weight B_n = B1*n/(B1*n + 1 - B1) and threshold Z*sqrt(1 - B1*B_n)*sigma_pop, with B1 seeded from published index-of-individuality values and labelled as borrowed. Ten lines of numpy, subsumes the SD floor, the confidence gate and the no-pre-op-data case, and surfaces baseline_confidence honestly.
- Conformal p-values as the replacement for the arbitrary composite thresholds 1.2/2.0 (backend/app/engine/composite.py:26-28), including the hard constraint that minimum attainable p is 1/(n_cal+1) and the requirement to degrade to 'insufficient calibration' below it. Right idea, right math, 25 lines of numpy — gated on actually capturing negative labels.
- Re-expressing trajectory deviation as ratio-to-own-pre-op-baseline rather than an absolute expected curve, and making a 7-14 day pre-op baseline window a hard enrolment requirement. Cheap, correct, and the Olanrewaju result (class membership driven overwhelmingly by pre-op step count) makes it the highest-value single change to the trajectory code.
- The refusals, all of them: no CNNs, no per-patient HMM/HSMM, no matrix profile on daily data, no SMOTE or class-imbalance correction, no isotonic calibration below 1000 events, no joint models, no deep survival, no end-to-end multimodal fusion, no fine-tuning of any foundation model in year one. These are correct and should be written down as standing policy so they are not relitigated.
- The Riley sample-size arithmetic and the conclusion that MedPull may not honestly describe the engine as risk prediction at current scale — a 6-parameter model needs ~1,300 patients, a 3-parameter model ~660. Put the computed number and the current adjudicated-event count on an internal dashboard so the gate is observable.
- Discrete-time pooled logistic hazard on person-day rows as the eventual learned model, explicitly served as a frozen numpy dot product with the composite deviation index entering as a SINGLE scalar covariate. This is the only proposal in the whole set whose serving story matches the actual deployment.
- The LLM contract as already implemented in spirit: deterministic engine computes every number, LLM renders prose only, temperature 0.2-0.3, plus a post-generation validator that regex-extracts every number in the output and asserts membership in the input payload, with retry-then-template fallback. Days of work, prevents the worst clinical failure mode, needs no new dependency.
- Silent/shadow deployment with pre-registered promotion criteria (>=90 days, >=30 completed episodes, >=5 high-tier events, alert burden within budget, clinician case-by-case review of disagreements) as the gate for every engine version — including parameter-only changes to EWMA/CUSUM/weights.
- Patient-level splits everywhere (GroupKFold / LeaveOneGroupOut on patient_id), PR-AUC and calibration slope over AUROC, and alerts-per-patient-week plus median lead time as the headline metrics clinicians are actually shown.
- Week-one replay of the production detector over LifeSnaps (n=71, Fitbit Sense, matches your six-metric panel) and PMData (n=16) to measure the false-alarm rate. Zero cost, zero patients, no IRB, ~9,000 person-days where every alert is false by construction, per-participant bootstrap for CIs. This is the single highest-value validation item on the entire list and it can start today.

## Verdict
Reject in present form; major revision required. The refusals in this proposal are all correct (no CNNs, no wearable foundation models, no joint models, no deep survival, no SMOTE, no isotonic calibration below 1000 events, no GBTM below 200 subjects) and the sourcing is unusually good. But four failures would produce confidently wrong output in production. (1) VALIDATION IS CIRCULAR, CONFIRMED IN CODE NOT MERELY AT RISK: app/seed/generators.py:20 does `from app.engine.curves import curve_mid, recovery_progress` and line 125 computes `level *= float(curve_mid(spec.procedure, eff)) * scenario.track`. Patients are drawn from the engine's own expected curve. curves.py's docstring admits it: "The seed generator shapes on-track patients along these same curves, so 'on track' is on track by construction." Every golden-tier test, ARL estimate and false-alarm rate you hold measures your RNG. Until that import edge is severed, no empirical claim here has evidentiary status. (2) EVERY ARL, p-VALUE AND CONFORMAL GUARANTEE ASSUMES INDEPENDENCE DAILY WEARABLE VITALS DO NOT HAVE. ARL0 ~780 (EWMA) and ~895 (CUSUM) are i.i.d.-normal numbers. At realistic lag-1 autocorrelation 0.4-0.7 for daily RHR/HRV/sleep, the EWMA statistic's variance inflates by roughly (1+phi(1-lambda))/(1-phi(1-lambda)) — about 2.08 at phi=0.5, lambda=0.3 — so the true SD is ~1.44x assumed and the nominal 2.66-sigma limit is really ~1.85 sigma; ARL0 falls close to an order of magnitude. The "2-consecutive-day rule is load-bearing" finding is the worst casualty, since consecutive days are exactly what autocorrelation correlates. The conformal p-values and the Ville/power-martingale bound inherit the same defect. (3) FOUR NEW UNVALIDATABLE LAYERS (BOCPD, MEWMA with an admittedly unverified control limit, adaptive conformal, online FDR) ARE PROPOSED ON TOP OF AN ENGINE WITH TWO OUTRIGHT BUGS IN ITS FOUNDATION: n=3 baselines that can anchor on the acute post-op perturbation, and a gap-blind EWMA recursion. Inverted priority. (4) THE DOCUMENT CONTRADICTS ITSELF ON SAMPLE SIZE: it derives Riley's floor at ~1,288 patients / 64 events, then licenses penalized logistic at 50 events, Firth at 40, and a 500-tree BalancedRandomForest at 30. Pick one number, put it in a constant, enforce it in CI. Counsel: this is a MONITORING INSTRUMENT, not risk prediction. The honest 12-month roadmap is six bug fixes, one exchangeability correction, an episode state machine, external ARL calibration on LifeSnaps/PMData, and a silent deployment — not eleven new statistical methods.

### Objections

**TARGET:** Validation strategy — app/seed/generators.py importing app/engine/curves.py

- **OBJECTION:** Confirmed circularity in shipped code, not a risk. generators.py:20 imports curve_mid and recovery_progress from the engine; line 125 computes level *= curve_mid(procedure, eff) * scenario.track. The engine is evaluated against data drawn from its own generative model, the only freedoms being scenario.track and additive noise. FUNCTIONAL_RATIO_SD = 0.10 (deviation.py:36) is therefore not an estimate of anything — it is a dial that solely determines how often the seed's track multiplier trips a flag. (b) Rewrite the generator with a DIFFERENT functional form than the engine's logistic — Mitscherlich r(d)=A(1-exp(-k(d-t0))) with A,k,t0 drawn per patient from literature-anchored distributions (Olanrewaju 2026, n=82: week-1 median ~360 steps, week-6 ~3,739, only ~1 in 3 exceeding pre-op by week 6) — so misspecification exists by construction, as in production. (c) Move all specificity/ARL calibration off seed data onto LifeSnaps (71 participants, Fitbit Sense, DOI 10.5281/zenodo.6826244) and PMData (16 participants): non-surgical, so every alert is a false positive by construction. Bootstrap per-participant, never per-day.

**TARGET:** ARL0 ~780 (EWMA) / ~895 (CUSUM), the '2-consecutive-day rule is load-bearing' finding, and the <=0.5 false-openings/patient-month budget

- **OBJECTION:** Computed under i.i.d. normality. Daily RHR, HRV RMSSD, sleep duration and skin temperature carry substantial positive lag-1 autocorrelation in free-living data (commonly 0.4-0.7 for RHR and sleep). deviation.py:81 uses EWMA_L*sqrt(LAMBDA/(2-LAMBDA)), the steady-state SD under independence ONLY. Under AR(1) variance inflates by ~(1+phi(1-lambda))/(1-phi(1-lambda)) = 2.08 at phi=0.5, lambda=0.3, so the true SD is ~1.44x assumed and your 2.66-sigma limit operates at ~1.85 sigma. The consecutive-day rule is worst hit because serial correlation is precisely what makes consecutive exceedances co-occur — its ARL0 multiplier collapses from ~4.6x toward ~1.5x. Note composite.py:35 uses raw_z deliberately, so the composite has zero temporal smoothing and inherits raw autocorrelation, evaluated daily for 90 days.
- **CONSEQUENCE:** True in-control ARL is plausibly 80-150 days rather than 780-895 — roughly one false alarm per patient per episode from the EWMA alone, before multiplying by 8 metrics and 2 detectors. You miss your own alert budget by about an order of magnitude, clinicians reach the 49-96% CDS override rates the proposal names as the failure to design against, and credibility is spent in the first pilot. You will not know, because the CI ARL simulation runs on i.i.d. seed data and keeps reporting 780.
- **FIX:** (a) Estimate phi per metric from your pre-op windows and from LifeSnaps; report it. (b) Interim: L_eff = 2.66*sqrt((1+phi_hat(1-lambda))/(1-phi_hat(1-lambda))), floored at 2.66, capped ~4.0, phi_hat shrunk toward a metric-level pooled value at weight n/(n+10) since 14 pre-op days will not estimate phi well. (c) Medium term adopt the Kalman-innovations idea — it IS the principled fix since one-step-ahead innovations are white by construction under a correct model — but ship a Ljung-Box test (lag 10, alpha=0.05) on the innovations as a runtime gate with fallback to the inflated-limit path when it rejects; without it you have relocated the assumption, not satisfied it. (d) Do NOT stack detectors: a local-level filter with fixed q=0.02 has steady-state gain K=(sqrt(q^2+4q)-q)/2 ~= 0.13, i.e. it IS an EWMA with lambda=0.13; running lambda=0.3 EWMA on its innovations is double smoothing whose ARL nobody has computed. (e) Re-run the CI ARL simulation with AR(1) at phi in {0,0.3,0.5,0.7} and publish the ARL0 surface, not a single number.

The post-op fallback is a patient-safety issue, not a statistics issue: a patient whose RHR is legitimately elevated and stays elevated scores z~0 (on track); a patient whose RHR normalizes scores NEGATIVE. **TARGET:** deviation.py:84-86 — EWMA recursion iterating a pandas Series with missing days simply absent; deviation.py:106 CUSUM slice

- **OBJECTION:** The series is indexed by post-op day but never reindexed onto a complete daily grid, so the recursion treats whatever days are present as consecutive. **TARGET:** composite.py — HIGH=2.0 / ELEVATED=1.2 on a weighted sum of five clipped, correlated, one-sided raw z-scores, plus the drivers contribution percentages at composite.py:44-52

- **OBJECTION:** Four compounding problems. (i) The clip min(max(z,0),4.0) makes each term a censored half-normal with mean ~0.399*sigma, so under the null the index has mean ~0.40, not 0 — 'normal' at <=1.2 is barely two null-SDs up. (ii) The five metrics are strongly positively correlated even in health (RHR, RR, temp and inverted HRV co-move; typical pairwise rho 0.3-0.6), so Var(sum) = sum w_i^2 sigma^2 + 2*sum_{i<j} w_i w_j rho_ij sigma^2 is roughly 2-2.5x the independence value at these weights: SD ~1.5x larger than any independence-based intuition, making 2.0 a far lower quantile than believed. (iii) It uses raw_z, so no temporal averaging at all, evaluated daily across 90 days. (iv) The drivers block reports each metric's share of a correlated sum as an independent contribution and shows it to clinicians; when RHR and temp are both up from one fever, the split is an artifact of the hand-set weights.
- **CONSEQUENCE:** The thresholds have no known false-positive rate under any distribution and the index is not comparable across patients, procedures or post-op days. Clinicians build mental models on a non-identifiable driver breakdown ('this one is temperature-driven') that do not survive a change of weight vector. Because the correlation is shared across patients (weather, firmware, a cold snap), false alarms arrive in CORRELATED BURSTS across the panel, which additionally voids the independence/PRDS assumption the proposed Benjamini-Hochberg step requires.
- **FIX:** (a) I endorse conformal p-values replacing the thresholds, subject to the exchangeability fix below — but calibrate the existing index; do not simultaneously swap it for MEWMA. (b) Immediately and independently: measure the null distribution of the index on LifeSnaps and set HIGH/ELEVATED as empirical quantiles of that external null, not round numbers. (c) Keep raw_z for responsiveness if you must, but then wrap daily evaluation in the episode state machine so one deterioration yields one alert, not forty. (d) Either delete the driver percentages or compute Shapley values over the correlated set (5 metrics = 32 coalitions, trivially cheap). (e) Reconsider skin temperature's 0.25 weight: wrist skin temp in free living is dominated by ambient conditions and bedding, and at a 0.12 degC floor a 0.4 degC ambient excursion yields z=+3.3 contributing 0.83 by itself — 70% of the elevated threshold from one confounded metric. Drop it pending an ambient correction, or score it against the patient's own trailing 7-day median with a 0.25 degC floor plus local ambient temperature as a covariate.

**TARGET:** Mondrian split-conformal: 'n_cal >= 99 days for alpha=0.01, >=19 for alpha=0.05', strata (procedure, postop-week bucket), plus power martingale epsilon=0.92 alarming at M_t>100 under Ville's inequality

- **OBJECTION:** The arithmetic is right and applied to the wrong n. Split conformal gives finite-sample marginal validity under EXCHANGEABILITY of calibration and test points. Patient-days are not exchangeable on two axes: within a patient they are serially dependent, and across a stratum they carry a strong day-since-surgery trend that bucketing into 1-7 / 8-21 / 22-90 reduces but does not remove — the day-22 and day-89 conditional distributions differ substantially, making p-values anti-conservative early in each bucket and conservative late. So '20 patients x 90 days = 1,800 rows, ample' is wrong: under strong within-patient dependence the effective sample size is nearer the number of PATIENTS (20-60) than of rows, and alpha=0.01 is unattainable at 20 patients whatever the row count says. The document contradicts itself — the CQR row correctly specifies patient-level splitting with one summary score per calibration patient, while the alerting row uses patient-days. Separately, Ville's inequality bounds P(exists t: M_t >= 100) <= 1/100 only for i.i.d. U(0,1) null p-values, which these are not, so the trajectory-level guarantee is void as specified.
- **CONSEQUENCE:** You ship a number labelled 'guaranteed 1% false-alarm rate' carrying no such guarantee, into a clinical product — worse than the current admittedly arbitrary 2.0, because an arbitrary threshold makes no promise. The failure is directional and predictable: anti-conservative early in each week bucket, so most false alarms land in post-op week 1 and at day 8, exactly where clinicians are already most anxious.
- **FIX:** (a) Make the PATIENT the exchangeable unit throughout, harmonizing with the CQR row: one summary conformity score per calibration patient (max over their days, or their 90th percentile — pick one, document it, report empirical coverage of each). n_cal is then completed uneventful PATIENTS, so alpha=0.05 needs >=19 patients and alpha=0.01 needs >=99; enforce in code, degrade to insufficient_calibration otherwise. Far stricter and more honest than the row-count version. (b) Replace 3 week-buckets with day-since-surgery as a finer Mondrian taxonomy with hierarchical smoothing, or better remove the trend before conformalizing by scoring residuals against the fitted expected curve so the conditional distribution is closer to stationary in day. (c) Measure and report empirical coverage on held-out patients; outside 85-95% for nominal 90%, say so publicly and treat exchangeability as broken. (d) Drop the power martingale. If you want anytime-validity, the CUSUM you already have IS a restart-at-zero SPRT and is the honest e-process here; a second sequential procedure with an unsatisfiable guarantee adds risk without information.

**TARGET:** MEWMA row — lambda=0.15, h4=16.0 for p=6 'interpolated, verify by simulation before shipping', pooled Ledoit-Wolf covariance across patients, billed as the principled replacement for hand-tuned weights

- **OBJECTION:** Three independent problems, any one disqualifying at this scale. (i) You are recommending an UNVERIFIED control limit; the published Prabhu-Runger/Lowry tables are indexed at specific lambda and the ARL surface is not linear in lambda, so interpolating h4 and shipping it is not defensible. (ii) The exact time-varying covariance form — which the proposal correctly insists on — makes the chart MOST sensitive at small i, i.e. the first days after surgery, when physiology is legitimately and massively perturbed; MEWMA will fire on essentially every patient at days 2-6. (iii) Most seriously, LedoitWolf across patients estimates the BETWEEN-patient correlation structure while the chart needs the WITHIN-patient day-to-day residual structure. These are different matrices; substituting one for the other is the ecological fallacy in covariance form — between-patient RHR/temp correlation is driven by body composition and demographics, within-patient day-to-day correlation by illness and ambient conditions, and they can differ in magnitude and sign. Finally, a Hotelling statistic is non-diagnostic by construction: it says 'something is off' without saying what, destroying the typed reason codes that are this product's most defensible asset.
- **CONSEQUENCE:** You replace a transparent, clinician-auditable, wrong-but-legible weighted sum with an opaque quadratic form built on the wrong covariance and an unverified limit, losing the reason codes in the trade. At ~200 patient-days per procedure you cannot validate a 6x6 covariance against any alternative, so you would never discover it is wrong. This is the clearest case in the document of a complex method that cannot be validated at this sample size.
- **FIX:** CUT MEWMA at this scale. Keep the fixed-weight composite with weights explicitly elicited from >=2 surgeons and documented as elicited (which the document elsewhere correctly recommends), calibrated by patient-level conformal p-values: a stated false-alarm rate AND retained reason codes. If revisiting past ~500 patients: (a) estimate covariance correctly — each patient's own residual correlation matrix over their post-op days, Fisher-z transform, average across patients weighted by (n_i-1), inverse-transform, shrink toward a diagonal target; (b) simulate the control limit for your exact (p, lambda, n) rather than interpolating, and pin the simulation in CI; (c) gate to postop day >= 14 so the time-varying limit has converged; (d) always pair T^2 with a decomposition (MYT or per-metric conditional contribution) so a reason code still exists.

**TARGET:** BOCPD row — hazard 1/35 on standardized Kalman innovations, NIG prior (mu0=0, kappa0=1, alpha0=2.0, beta0=1.0), reason code when P(r_t<3)>0.5

- **OBJECTION:** Unvalidatable, will fire constantly, and fights the layer beneath it. (i) Hazard 1/35 over 90 days carries a PRIOR expectation of ~2.6 changepoints per patient per episode before any data; with a loose emit rule of P(r_t<3)>0.5 it will produce changepoint codes on most patients most weeks. (ii) The NIG prior with beta0=1.0 assumes innovations are truly unit-variance, which holds only if q is correctly specified — and q is FIXED BY FIAT at 0.02 for the n<60 case, which is every patient during the clinically relevant window. (iii) The local-level Kalman filter directly upstream is DESIGNED to absorb slow level drift into the state, so gradual regime change is partly swallowed before BOCPD sees it — a change detector downstream of a change absorber. (iv) Six streams per patient with no multiplicity handling mentioned. (v) There is no ground truth for 'recovery changed character on day 34'; you can never measure its precision at your scale.

**TARGET:** Multiplicity handling — Benjamini-Hochberg at q=0.10 across the panel each morning, plus SAFFRON/ADDIS online FDR over episode openings

BH across the morning list controls the false-discovery proportion among PATIENTS FLAGGED TODAY and does nothing about one patient generating forty alerts across an episode, which is the alert-fatigue mechanism that actually kills clinical products. The ordering is inverted too: the episode state machine is listed as a governance nicety while FDR machinery is presented as the multiplicity solution, when the state machine IS the multiplicity control and FDR is a refinement on top. BH also requires independence or PRDS, and per-patient conformal p-values on a given morning share device model, firmware version, weather and season — plausible PRDS violations, and the correlated-burst failure mode from the composite objection lands exactly here.

### Endorsed
- Restricting vitals to a nocturnal window (00:00-07:00, zero-step minutes) — the cheapest accuracy improvement available; removes activity confounding from RHR/HRV/RR and is well supported across the wearable illness-detection literature.
- NightSignal as a simple, auditable, per-patient headline detector (streaming median; +3 bpm one night = yellow, +4 bpm two consecutive = red). CAVEAT: its 80% sensitivity / 87.7% specificity was for COVID onset in an otherwise healthy population, not complication onset in patients whose RHR is legitimately elevated for weeks — expect materially worse specificity. Seed the streaming median from the PRE-OP median and exclude post-op days 0-14 from it, or the baseline chases the surgical perturbation itself.
- Parametric empirical Bayes shrinkage for baselines (Roys 2025): B_n = B1*n/(B1*n + 1 - B1), threshold Z*sqrt(1 - B1*B_n)*sigma_pop. Correctly subsumes the SD-floor hack, the confidence gate and the no-pre-op-data case in one closed form, runs in microseconds, degrades gracefully. Z=3.0 rather than 1.96 is right at 6 metrics x 365 days. Use literature priors below 30 patients and LABEL THEM AS SUCH.
- Moderated (empirical-Bayes) variance sigma_i^2 = (nu0*sigma_pop^2 + (n_i-1)*s_i^2)/(nu0 + n_i - 1) with nu0=8, robust scale (MAD scale='normal' below n=5, Huber c=1.345 above), median as centre, hard floors only at device resolution. The correct replacement for the SD floors, and it should ship first.
- Ratio-to-own-pre-op-baseline rather than absolute scale for functional metrics, with pre-op step count as a COVARIATE in the expected curve rather than a nuisance. The Olanrewaju 2026 result (n=82; class membership driven overwhelmingly by pre-op step count; only 32% exceed pre-op by week 6) is directly on point and correctly indicts absolute-scale curves.
- Making a 7-14 day pre-op capture window a hard enrolment requirement. This is your genuine differentiator over both Ghomrawi 2023 and Hua 2025, who list its absence as their top limitation, and the entire shrinkage stack depends on it.
- Per-metric monotone transforms fitted once on pooled data and FROZEN as versioned constants — ln(RMSSD), ln(1+steps), Yeo-Johnson for signed temperature deviation. Treating a change in lambda as a breaking change to every stored z-score and threshold is exactly right.
- Patient-level grouping in every split — LeaveOneGroupOut / StratifiedGroupKFold on patient_id, never a random split. The warning that a random split inflates AUC by 0.1+ is if anything understated for daily-resolution data.
- Harrell enhanced-bootstrap optimism correction with the FULL pipeline (threshold selection, weight fitting, calibration) inside the loop, B=500, resampling PATIENTS not rows. Non-negotiable and correctly specified.
- Alert burden per patient-week — not AUROC — as the primary design metric, with AUPRC and calibration slope/intercept ahead of AUROC in reporting. The Ghomrawi/Hua AUPRC figures of 0.36 and 0.14 against AUROC 0.80/0.86 make the case decisively.
- Decision curve analysis with clinician-elicited harm ratios, pt = 1/(R+1) from 'R false alarms tolerated per true catch', elicited from >=2 surgeons per tier. The right way to set thresholds, and it works today at zero events as an elicitation exercise.
- Discrete-time hazard via pooled logistic regression on person-day rows as the eventual supervised frame, with cluster-robust SEs (cov_type='cluster' on patient_id), a restricted cubic spline baseline in post-op day, the composite index entered as ONE scalar covariate, horizons 7/14/30 all derived from one fitted daily hazard, and no class weighting or SMOTE. Correct on every count, and correctly gated behind an event floor.
- The full list of refusals: no CNNs, no per-patient HMM/HSMM, no matrix profile on daily data, no wearable foundation models (the modality-mismatch argument is decisive — daily aggregates fit none of them), no LLM-based forecasters, no joint models, no deep survival, no SMOTE or imbalance correction, no isotonic calibration below 1,000 events, no GBTM/LCGA below 200 subjects, no LMS/GAMLSS centiles at your n, no GPyTorch. Every one is right and several are non-obvious.

The correct pattern, and the numeric-consistency validator is the load-bearing part.
